# Construction Video Prompt Engineering

Current version: `v0.1`

Generate copy-ready prompts for short engineering construction-process videos from a user's natural-language description of the construction stage, intended action, and desired visual effect.

This skill is for controlled construction visualization. It prioritizes stage correctness, component identity, spatial boundaries, action direction, and endpoint alignment over generic cinematic language. First/last frames are not required by the skill; the generated prompt is first/last-frame-ready by default, and users usually upload those frames later to the video model together with it.

## Model Scope and Compatibility

This skill is model-agnostic at the language level, but it is designed primarily for
short construction clips generated by a video workflow that accepts:

- a text prompt describing one controlled construction action;
- a starting image and an ending image, or an equivalent first/last-frame condition;
- optional positive and negative prompt fields;
- a workflow that can preserve the supplied scene while synthesizing the motion between
  the two states.

### Primary project-aligned target

The most directly aligned target in this project is a native ComfyUI / RunningHub
**Wan 2.2 FLF2V** workflow. Its observed structure includes:

- Wan 2.2 high-noise and low-noise I2V 14B model files;
- Wan UMT5 text encoder and Wan VAE;
- separate start-frame and end-frame image inputs;
- a `WanFirstLastFrameToVideo` node;
- positive and negative text-conditioning nodes;
- video creation and save nodes.

The skill's default output is therefore suitable for this workflow shape: the positive
prompt describes the construction action and endpoint transition, while the negative
prompt targets camera drift, geometry changes, premature stages, duplicated equipment,
and other construction-specific failures. The skill does not claim that a particular
seed, sampler, resolution, or model revision will always reproduce a result.

### Important distinction: the supplied hammer-pile workflow

The supplied hammer-pile workflow JSON does not itself identify a video-generation
model. Its node graph contains no `WanFirstLastFrameToVideo`, `CreateVideo`, or
`SaveVideo` node, and it does not load a Wan or other video-model checkpoint. The
word `video` in workflow metadata is not evidence that the graph generates video.

The supplied hammer-pile RunningHub / ComfyUI JSON is **not a video-generation
workflow**. It is an upstream keyframe-realization workflow with:

- the `RealVisXL V5.0 (BakedVAE) fp32` SDXL checkpoint;
- SDXL Canny and Depth Control-LoRA conditioning;
- a two-pass KSampler pipeline;
- a machinery inpaint mask;
- `SaveImage` outputs and no `WanFirstLastFrameToVideo`, `CreateVideo`, or
  `SaveVideo` node.

Its role is to turn Blender or BIM keyframes into more realistic start and end images.
Those images can then be supplied to a downstream video model such as Wan 2.2 FLF2V.
`RealVisXL V5.0` is consequently a supported **keyframe-preparation context**, not a
video model that this skill directly drives.

The downstream video-model compatibility described below comes from the separate
project workflow shape used for video generation: **Wan 2.2 FLF2V** with start-frame
and end-frame inputs. The two workflows form a pipeline:

```text
Blender / BIM keyframe
    -> RealVisXL V5.0 + SDXL Canny/Depth + inpaint
    -> realistic start/end keyframes
    -> Wan 2.2 FLF2V video workflow
    -> short construction video clip
```

### Compatibility levels

| Target workflow or model type | Compatibility | How to use this skill |
|---|---|---|
| Wan 2.2 FLF2V in ComfyUI / RunningHub | Primary, project-aligned | Use the default English positive and negative prompts with the matching start and end frames. |
| Other Wan FLF2V or VACE first/last-frame workflows | Good, workflow-dependent | Keep the semantic prompt structure; verify the actual node's frame order, prompt fields, negative-prompt behavior, and resolution limits. |
| Other first/last-frame or start/end-frame video models | Applicable with adaptation | Preserve the construction constraints, but adapt field names and syntax to the provider. |
| Single-image image-to-video models | Partial | Use the action and invariant-object rules, but remove or rewrite the unsupported second-endpoint instruction. |
| Pure text-to-video models | Limited | Ask explicitly for pure text-to-video so endpoint wording is omitted; expect less structural control without reference frames. |
| SDXL/RealVisXL image-realization workflows | Upstream only | Use them to prepare realistic keyframes; they do not generate the final video. |

Models such as hosted cinematic video services may accept the semantic prompt, but this
skill does not assume that they support first/last-frame conditioning, negative prompts,
or the same prompt syntax. Mark those capabilities as unverified until the actual
workflow is checked.

In short, this skill is best understood as a **semantic prompt layer for
frame-conditioned construction video workflows**. It is not tied to the
`RealVisXL V5.0` checkpoint, does not generate the keyframes or video itself, and
does not require a particular sampler, seed, resolution, or provider API.

## Actual Usage

After installing the skill:

1. Describe one construction clip in natural language.
2. State the action and visible effect you want, plus the objects, camera, area, and later-stage content that must be controlled.
3. Ask the agent to write the prompt. Do not upload first/last frames to the agent unless you want wording refinement.
4. Copy the generated positive and negative prompts into the target video model.
5. Upload the corresponding first and last frames to that model and run its compatible frame-conditioned workflow.

The skill handles step 3 only. It does not create the frame pair, run the model, or inspect the generated video unless you explicitly ask for a separate repair or QA task.

## What It Produces

For an ordinary prompt request, the skill produces prompt text only:

1. A copy-ready English positive prompt for the video model.
2. A copy-ready English negative prompt.
3. Chinese positive and negative prompts for human review when useful.
4. A short assumptions note when the prompt depends on an unstated choice.
5. A focused repair prompt when an observed failure is supplied.

It builds an internal state card to reason about the clip, but it does not expose full case records, benchmark reports, or media QA during ordinary prompt writing.

## Before You Use It

Describe one clip at a time. You do not need to upload frames to get a prompt. The minimum useful description is:

```yaml
construction_stage: "for example: single precast-pile hammer driving"
primary_action: "one action only"
desired_effect: "what the viewer should clearly see"
camera_behavior: "fixed camera, close-up, pullback, or unknown"
locked_objects: "what must stay fixed"
allowed_change: "what may change in this clip"
action_direction_and_area: "where and in which direction it changes"
forbidden_content: "later-stage or unrelated content"
target_platform_or_workflow: "optional"
output_requirements: "optional duration, aspect ratio, resolution, fps"
observed_failure: "optional visible failure in an existing result"
```

The description should identify one main operation. If frames are supplied to the agent, use them to refine the wording. If frames are not supplied, write a first/last-frame-ready prompt by default; omit endpoint wording only when the user explicitly requests pure text-to-video. Keep a fixed camera when the construction state changes unless a camera move is explicitly intended. Split several independent operations into separate clips.

## Quick Example

```text
Write a prompt for a fixed-camera first/last-frame excavation clip.
The retaining wall and excavator must remain fixed. Only the exposed soil inside
the pit may be removed from the top downward. The visual effect should clearly
show the excavation depth changing. Do not show the next excavation layer,
workers, labels, or water. I will upload the first and last frames to the video
model later. Produce copy-ready Chinese and English positive and negative prompts.
```

## Boundaries

This skill does not:

- run paid generation jobs or guarantee a model result;
- require, inspect, or create first/last-frame images for an ordinary prompt request;
- require users to create a benchmark case before using the skill;
- certify construction safety, engineering compliance, or construction sequencing;
- infer model ID, seed, parameters, or permission status from filenames;
- replace video editing, narration, or post-production;
- bundle private BIM files, large media collections, model weights, credentials, or cloud task URLs.

## Testing

The text-only release tests are in [`evals/evals.json`](evals/evals.json). Run them according to [`evals/README.md`](evals/README.md). They test whether the skill can generate copy-ready prompts from descriptions without frames, refine a prompt when frames are supplied, repair observed failures, handle ambiguity, and avoid unsupported claims.

These generic tests do not prove that a particular video model produces high-quality video. Use a separate, rights-cleared benchmark package for media-based validation.

## Internal Benchmark Evidence

The hammer-pile project is an internal domain benchmark, not part of this public skill package. It is useful for:

- checking whether a revised skill still preserves real construction constraints;
- validating fixed-camera, machinery-lock, action-direction, and group-order reasoning;
- selecting a small, rights-cleared public case bundle later.

Do not publish its videos, high-resolution frames, BIM files, or workflow assets unless their technical provenance and redistribution rights are confirmed.

Before publishing a public release:

1. Run the description-first text-only eval cases and save a results record.
2. Run the skill validator and the Python script checks.
